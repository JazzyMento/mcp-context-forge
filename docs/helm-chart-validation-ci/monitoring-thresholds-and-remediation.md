# Monitoring Thresholds and Remediation

This document explains the monitoring signals used in the MCP Gateway Helm chart validation workflow, the example thresholds, what cause of failures could mean, and follow-up actions that can be taken.

| Area monitored | Observed through | When to investigate | What failure could mean | Remediation / follow-up action |
|---|---|---|---|---|
| MCP Gateway availability | Helm `gateway-health-test`, `/health` endpoint | `/health` fails or returns an error | Gateway may be unavailable, service name may be wrong, or pod may not be ready | Check Helm test logs, `kubectl get pods`, `kubectl describe pod`,  `kubectl get svc`, gateway logs and Helm values to try to identify what the failure could be caused by |
| Postgres service discovery | Helm `db-ready-test`, `nslookup mcp-stack-postgres.default.svc.cluster.local` | DNS lookup fails | Postgres service may not exist, service name may be wrong, namespace may be wrong, or chart config may be incorrect | Check `kubectl get svc`, `kubectl get pods`, Helm values, service template and `db-ready-test` logs to help identify whether the failure is caused by a missing service, incorrect service name, namespace mismatch or chart configuration issue|
| Pod readiness | `kubectl get pods -A` runtime snapshot | Any core pod not `Running` or not `Ready` after deployment wait period | Application or dependency failed to start | Use `kubectl describe pod`, `kubectl logs`, check image pull errors, config, secrets and resource limits to help identify why the pod isn't Ready |
| Pod restarts | `kubectl get pods -A` | Unexpected restart count greater than `0` for a new deployment | CrashLoopBackOff, app error, config problem or dependency failure | Inspect logs, events, environment variables, secrets and readiness/liveness probes to help identify whether the pod is crashing, misconfigured or failing Kubernetes health checks |
| Node CPU usage | `kubectl top nodes`, Grafana CPU dashboard | Sustained CPU above `80%` | Cluster node may be under resource pressure | Check high-CPU pods with `kubectl top pods` and review resource requests/limits and scaling options to help identify whether the node is overloaded, under-resourced, or needs more scaling|
| Pod CPU usage | `kubectl top pods -A` | MCP Gateway or database pod sustained above expected usage, e.g. `80%` of limit | App may be overloaded or under-resourced | Review traffic, resource requests/limits, HPA settings and logs to help determine whether the pod is overloaded, under-resourced, needs scaling or is failing due to an application issue|
| Pod memory usage | `kubectl top pods -A` | Memory close to configured limit, e.g. above `80%` | Risk of `OOMKilled` events or pod restarts | Review memory limits, logs, memory trend, pod restarts and application behaviour to help identify if the pod is using too much memory or being restarted due to memory pressure |
| Prometheus target status | Prometheus targets page, `up` query | `up == 0` for an important target | Prometheus cannot scrape a target, target is down, or scrape config is wrong | Check pod/service status, target endpoint, namespace, scrape config and logs to help identify why Prometheus cannot collect metrics from the target|
| Metrics API availability | `kubectl top nodes`, `kubectl top pods -A` | CPU/memory values are missing or command returns `Metrics API not available` | metrics-server may not be installed, ready, or able to scrape node metrics in the temporary Kind cluster | Check metrics-server pod status, rollout status and logs, confirm Kind metrics-server patch is applied, then rerun after metrics-server has time to collect data |
| Gateway smoke test | `smoke-test-gateway-health`, `check_gateway_health.py` | Smoke test fails against the running `/health` endpoint | Gateway may not be reachable through port-forwarding, endpoint may not return HTTP 200, or response body may not contain `status=healthy` | Check port-forward is running, confirm service name and port, run `curl http://127.0.0.1:4444/health`, inspect gateway logs to help identify whether the gateway is unreachable, misconfigured, or returning an unhealthy response. Then rerun the smoke test |
